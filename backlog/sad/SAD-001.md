## SAD#1 Context & Scope

The Technical Stock Screener is a single-tenant web application for
self-directed technical traders. It collapses four normally-disconnected
contexts — building a screen, seeing which names match and *why*, confirming a
name on an interactive chart with the screen's overlays, and backtesting the
screen's forward returns — into one loop.

The system is derived from a working prototype in `poc/` that already proves the
full screen → results → detail → backtest loop against a synthetic universe. The
React + TypeScript + Vite application in `src/` is the real product surface; the
indicator/rule/backtest engine has been ported to `src/lib/market.ts` as a
dependency-free pure module. The architectural problem this SAD solves is
**keeping the POC's proven product surface and numeric semantics while replacing
its three load-bearing fictions: synthetic data, browser-only compute, and
in-memory persistence.**

**Primary actor:** an authenticated-or-anonymous single user (no multi-user
collaboration in this scope — see SAD#1.2).

**System boundary:** inside = the screening web app, the screening/backtest
compute path, a market-data ingestion/adjustment boundary, and persistence of
user-authored artifacts. Outside = the upstream market-data vendor, any
brokerage, and any real trading or order flow.

### SAD#1.1 In scope
- Composable rule-based universe screening with AND/OR grouping (engine parity
  with the POC).
- Strategy preset library plus user create/edit/delete of custom presets.
- Custom indicator builder (EMA/SMA/RSI/MACD/Stoch-RSI) over selectable sources.
- Setup / condition-group builder (pairwise comparisons, bar offsets,
  ×mult/+add arithmetic, cross-up/cross-down).
- TC2000 PCF paste → condition group, over the **supported operator/indicator
  subset only** (SAD#3.5, SAD#8 ADR-009).
- Named screens (ordered comparison chains).
- Price-action pattern filters and cross-sectional ranking.
- Results view: matches grouped by sector, session diff banner, empty-state
  "loosen a rule" guidance.
- Interactive candlestick detail chart with screen overlays, indicator panes,
  signal markers, and per-rule "why it fired" explainability.
- Side-by-side stock comparison.
- Backtesting: forward returns at 5/10/20-bar horizons with fire/win-rate stats.
- Ticker/company search and quick-signal toggles.
- Running on **real, corporate-action-adjusted daily market data** behind a
  provider abstraction.
- Screening and backtesting that **scale past browser-only compute** to a
  production universe of thousands of names.
- Persistence of user-authored artifacts (indicators, presets, named screens)
  across sessions behind a storage boundary.

### SAD#1.2 Out of scope (non-goals)
> This list is a primary scope-creep defense. A story that builds something
> here is invalid by definition. Carried verbatim from PLAN-001.

- **The `dc-runtime` prototyping harness is not the product.** `support.js` and
  the `.dc.html` "deckcode" format are a demo renderer; the real app is the
  React + TypeScript + Vite project already scaffolded in `src/`. Do not carry
  `<x-dc>`, `sc-for`/`sc-if`, or the `data-dc-script` mechanism forward.
- **The synthetic market universe is not a data source.** The seeded
  `mulberry32` random-walk generator, the 43 hardcoded tickers, the faked
  "ends today" weekday dates, and the ~260-bar history are demo fixtures, not a
  feed to be productionized.
- No accounts, auth, or multi-user collaboration in this scope (but see Open
  questions — persistence of saved artifacts likely forces this soon).
- No portfolio/order management, brokerage integration, or real trading.
- No intraday/real-time streaming in v1 (the POC is daily-bar, end-of-day).
- Not a TC2000 clone: full PCF-language coverage beyond the operators the POC
  supports is out of scope unless explicitly committed.

## SAD#2 Quality Attributes & Constraints

Each attribute is phrased so a story can be checked against it.

### SAD#2.1 Numeric fidelity (highest priority)
Indicator math and rule semantics **must match the POC engine exactly**:
EMA/SMA, RSI with Wilder smoothing, Stoch-RSI, MACD/MACD-full, AND/OR grouping,
bar offsets, cross-overs, and the supported TC2000 PCF dialect.
**Posture:** a golden-master test suite pins every engine function's output to
the POC's output bar-for-bar over a fixed fixture series; any divergence fails
CI. Traders won't trust numbers that disagree with TC2000 or the chart.

### SAD#2.2 Data correctness
All bars consumed by the engine are **split- and dividend-adjusted** before they
reach indicator math. **Rule:** the engine never sees unadjusted closes;
adjustment is the data layer's responsibility (SAD#6.1). **Posture:** an
adjustment test asserts a known split is reflected in the adjusted series.

### SAD#2.3 Screening latency
A full-universe screen (production universe, thousands of names) must return
within a stated interactive budget. **Budget (v1 target):** p95 ≤ 3 s for a
warm-cache full-universe screen; a single-name re-evaluation for the detail view
is local and ≤ 50 ms. Stories that touch the screen path must not regress p95
beyond budget.

### SAD#2.4 Backtest latency
A backtest of one screen over the full universe and full available history
completes within a stated batch budget. **Budget (v1 target):** ≤ 30 s server-
side for the full universe; results are returned as a single summary payload
(SAD#6.5). Long-running backtests must report progress, not block the UI thread.

### SAD#2.5 Scalability
The architecture must not assume "compute every indicator for every bar of every
name in the browser." **Rule:** full-universe screen and backtest run server-
side over a shared engine; the client computes only for the names it displays
(detail, compare, small ad-hoc sets). See SAD#8 ADR-003.

### SAD#2.6 Portability of the engine
The engine remains a **dependency-free, side-effect-free, isomorphic ES module**
runnable unchanged in both the browser and Node. **Rule:** no DOM, no `fetch`,
no global state, no date-of-"today" assumptions inside `src/lib/market.ts`.

### SAD#2.7 Compliance posture
The product surfaces buy/sell-flavored signals. **Rule:** every results, detail,
and backtest surface carries a persistent "not investment advice" disclosure;
backtest results are labelled as naive/illustrative until SAD#3.11 rigor is
committed. Market-data redistribution must respect the vendor license
(SAD#8 ADR-008). No story ships a signal surface without the disclosure.

### SAD#2.8 Persistence durability
User-authored artifacts (indicators, presets, named screens) **survive across
sessions** and are accessed behind a repository interface (SAD#6.4), so the
backing store can change without touching feature code. **Posture:** create an
artifact, reload, confirm it is still present.

### SAD#2.9 Accessibility & responsiveness
Interactive charts and builder modals are keyboard-operable and the app is
usable at common desktop widths. **Posture:** builder modals are reachable and
dismissable by keyboard; chart pan/zoom has non-pointer fallbacks.

## SAD#3 Capabilities

Capabilities are the unit of work for the build loop. Each has a stable id and
an explicit acceptance posture. Capability ids are `CAP-screen`, etc.

### SAD#3.1 CAP-screen: Universe screening with composable rules
- **What it does:** evaluates a rule set against the universe with AND/OR
  grouping; an empty rule set returns the full universe. Routes across rule
  kinds (`num`/`flag`/`ema`/`ind`/`chain`/`group`/`pattern`/`rank`).
- **Primary components:** SAD#5.1 (engine), SAD#5.7 (screening service),
  SAD#5.2 (results view), SAD#5.9 (store).
- **Acceptance posture:** for a fixed fixture universe + rule set, the matched
  set equals the POC's `evalGroupedRules` output exactly; runs within SAD#2.3.

### SAD#3.2 CAP-presets: Strategy presets (built-in + custom CRUD)
- **What it does:** ships the built-in `PRESETS` library (oversold-in-uptrend,
  MACD momentum, fresh MACD cross, volume breakout, Stoch-RSI turn, trend
  pullback, six TC2000 setups) and lets the user create/edit/delete custom
  presets.
- **Primary components:** SAD#5.3 (PresetBuilder), SAD#5.6 (catalogues),
  SAD#5.8 (artifact repositories).
- **Acceptance posture:** applying any built-in preset reproduces the POC's
  match set; a custom preset round-trips through persistence (SAD#2.8).

### SAD#3.3 CAP-indicators: Custom indicator builder
- **What it does:** builds EMA/SMA/RSI/MACD/Stoch-RSI indicators over a chosen
  source (close/open/high/low/hl2/hlc3/volume) with per-type parameter schema +
  defaults; saved indicators become screenable and chartable.
- **Primary components:** SAD#5.3 (IndicatorBuilder), SAD#5.1 (`indSeries`),
  SAD#5.6 (`INDICATOR_TYPES`/`IND_DEFAULTS`/`SOURCES`), SAD#5.8.
- **Acceptance posture:** a built indicator's series matches the POC for the
  same def; the def round-trips through persistence and is selectable in rules
  and on the chart.

### SAD#3.4 CAP-setups: Setup / condition-group builder
- **What it does:** pairwise comparisons combined with AND/OR, each operand
  carrying a bar offset (t−1, t−2…) and optional ×mult/+add arithmetic;
  cross-up/cross-down operators.
- **Primary components:** SAD#5.3 (ScreenBuilder), SAD#5.1 (`evalGroupAt`/
  `evalCondAt`).
- **Acceptance posture:** a condition group with offsets and arithmetic
  evaluates identically to the POC `evalCondAt`/`evalGroupAt`.

### SAD#3.5 CAP-pcf: TC2000 PCF paste
- **What it does:** parses pasted Personal Criteria Formula text (`C > XAVGC50
  AND ...`, `XAVGC18>XAVGC50`, `.n` offsets, arithmetic, AND/OR) into a
  condition group, with a "Load example" sample, over the **supported subset
  only**.
- **Primary components:** SAD#5.1 (`parsePCF`/`parsePcfOperand`/`parsePcfBase`),
  SAD#5.3.
- **Acceptance posture:** the example PCF and the POC's PCF test cases parse to
  the same condition group; unsupported syntax fails with a clear, non-silent
  error (see SAD#8 ADR-009).

### SAD#3.6 CAP-screens: Named screens (chains)
- **What it does:** ordered comparison chains (e.g. `EMA18 > 50 > 100 > 200`)
  saved by name and reused.
- **Primary components:** SAD#5.3 (Screens UI), SAD#5.1 (`evalChainAt`), SAD#5.8.
- **Acceptance posture:** a saved chain evaluates identically to the POC and
  survives a reload.

### SAD#3.7 CAP-patterns: Price-action pattern filters
- **What it does:** consecutive up/down, higher/lower highs+lows, inside/outside
  bar, bull/bear engulfing, gaps, N-bar high/low breakouts, RSI bull/bear
  divergence, doji.
- **Primary components:** SAD#5.1 (`evalPatternAt`), SAD#5.6 (`PATTERNS`).
- **Acceptance posture:** each pattern flag matches the POC over the fixture
  series.

### SAD#3.8 CAP-rank: Cross-sectional ranking
- **What it does:** top/bottom percentile by a field, across the whole universe
  or within each sector. **Excluded from backtests** (matches POC).
- **Primary components:** SAD#5.1 (`rankPassSet`), SAD#5.6 (`RANK_FIELDS`),
  SAD#5.7.
- **Acceptance posture:** rank pass-set matches the POC; backtest path refuses
  or ignores rank rules exactly as the POC does.

### SAD#3.9 CAP-results: Results view
- **What it does:** matches grouped by sector, a session **diff banner**
  ("what changed vs the last screen"), and empty-state "loosen a rule" guidance.
- **Primary components:** SAD#5.2 (Results), SAD#5.9 (store, holds last-screen
  snapshot for the diff).
- **Acceptance posture:** sector grouping and the diff banner reproduce the POC
  behaviour; carries the SAD#2.7 disclosure.

### SAD#3.10 CAP-detail: Interactive detail chart + per-rule explainability
- **What it does:** candlesticks with EMA(9/20/50/200) overlays, volume/MACD/RSI/
  Stoch panes, pan/zoom/double-click-reset, panel toggles, signal markers where
  the screen fires, dashed overlays for custom price-scale indicators referenced
  by rules, and per-rule pass/fail with a "why did this fire" sparkline
  (`whySpark`).
- **Primary components:** SAD#5.4 (StockDetail/DetailPanels), SAD#5.5 (Spark),
  SAD#5.1 (single-name re-eval).
- **Acceptance posture:** overlays and signal markers align with the engine's
  fire bars; per-rule trace matches `evalRuleAt` results; single-name eval meets
  SAD#2.3's 50 ms budget.

### SAD#3.11 CAP-backtest: Backtesting
- **What it does:** walks every bar of every name; forward returns at 5/10/20
  horizons with fire rate, win rate, avg/median/best/worst; 30-bar warmup.
  **v1 fidelity is naive** (no costs/slippage/sizing/significance) and labelled
  as such (SAD#2.7).
- **Primary components:** SAD#5.1 (`backtestRules`), SAD#5.7 (backtest job),
  SAD#5.4 (BacktestModal).
- **Acceptance posture:** backtest summary matches the POC `backtestRules`
  output for a fixture screen; runs within SAD#2.4; result carries the
  naive-fidelity label.

### SAD#3.12 CAP-compare: Stock comparison
- **What it does:** a compare bar + drawer for side-by-side names.
- **Primary components:** SAD#5.4 (Compare), SAD#5.9 (store).
- **Acceptance posture:** selected names render side-by-side with consistent
  overlays; selection survives navigation within a session.

### SAD#3.13 CAP-search: Search & quick signals
- **What it does:** ticker/company search; golden/death cross, MACD/Stoch
  crosses surfaced as quick toggles.
- **Primary components:** SAD#5.2 (TopBar/search), SAD#5.6 (quick-signal
  catalogue), SAD#5.1.
- **Acceptance posture:** search returns expected names; each quick-signal
  toggle injects the equivalent rule the POC injects.

## SAD#4 Containers

### SAD#4.1 Web client (React + TypeScript + Vite SPA)
The product surface. React 19 + Vite + Zustand + react-router-dom +
@tanstack/react-table, already scaffolded in `src/`. Renders all builders,
results, detail charts, compare, and backtest UI. Runs the engine locally for
single-name/detail/compare and small ad-hoc sets. Talks to the screening
service over HTTP/JSON. Communicates with SAD#4.2 and SAD#4.4.

### SAD#4.2 Screening service (Node)
Server-side host of the **same** `src/lib/market.ts` engine, running full-
universe screens and backtests over the production data set. Exposes a small
HTTP/JSON API (screen, backtest). Stateless w.r.t. user data; reads bars from
SAD#4.3. Chosen so the scale-bound work (SAD#2.5) leaves the browser without
forking the engine (SAD#2.6, SAD#8 ADR-003).

### SAD#4.3 Market-data store + ingestion boundary
Holds adjusted daily OHLCV bars and universe membership/metadata for the
production universe. Behind the `MarketDataProvider` port (SAD#5.10): the
synthetic generator becomes one dev/test adapter; the licensed vendor becomes
another. Corporate-action adjustment happens here, before bars reach the engine
(SAD#2.2, SAD#8 ADR-005). **Vendor selection is an open question (SAD#8
ADR-008, proposed).**

### SAD#4.4 Artifact persistence
Stores user-authored indicators, presets, and named screens behind the
repository interface (SAD#5.8 / SAD#6.4). v1 backing store is deliberately
deferred behind the interface (SAD#8 ADR-006); accounts/auth remain out of
scope (SAD#1.2) until persistence forces them.

## SAD#5 Components

Patterns to use and to avoid are called out because stories cite this section
most.

### SAD#5.1 Engine — `src/lib/market.ts`
The ported POC `market.js`: indicator math (`ema`, `sma`, `rsi` Wilder,
`stochRsi`, `macd`/`macdFull`, `indSeries` with `defSig` caching), the rule
engine (`evalRuleAt`, `evalGroupedRules`/`evalGroupAt`, `evalChainAt`,
`evalCondAt`, `evalIndRuleAt`, `evalPatternAt`, `rankPassSet`), the PCF parser
(`parsePCF`/`parsePcfOperand`/`parsePcfBase`), and `backtestRules`.
- **Use:** keep it a pure, isomorphic, dependency-free ES module (SAD#2.6);
  preserve function names and semantics; add types without changing behaviour;
  pin behaviour with golden-master tests (SAD#2.1).
- **Avoid:** importing DOM/React/`fetch`; reading wall-clock "today"; embedding
  the synthetic generator; changing smoothing or rounding.

### SAD#5.2 Results & shell — `Results.tsx`, `TopBar.tsx`, `App.tsx`/`AppScreener.tsx`
Sector-grouped results table (@tanstack/react-table), session diff banner,
empty-state guidance, search, and quick-signal toggles; app shell + routing.
- **Use:** drive all data from the store (SAD#5.9); render the SAD#2.7
  disclosure here.
- **Avoid:** recomputing the universe in the table; duplicating engine logic in
  components.

### SAD#5.3 Sidebar & builder modals
`Sidebar.tsx` + `sidebar/*` (ActiveFilters, FilterSections, Indicators,
Presets, QuickSignals, Screens) and `modals/*` (IndicatorBuilderModal,
PresetBuilderModal, ScreenBuilderModal). Author indicators, presets, condition
groups/chains, and PCF paste.
- **Use:** read schemas/defaults from the catalogues (SAD#5.6); write artifacts
  through the repositories (SAD#5.8); produce rule objects the engine consumes
  unchanged.
- **Avoid:** hardcoding indicator/source/operator lists inline — they live in
  the catalogues.

### SAD#5.4 Detail, panels, compare, backtest — `detail/*`, `compare/*`, `modals/BacktestModal.tsx`
Interactive candlestick chart + indicator panes, per-rule explainability,
side-by-side compare, and the backtest launcher/results UI.
- **Use:** call the engine locally for single-name detail/compare (SAD#2.3);
  request full-universe backtests from SAD#4.2 and render the returned summary
  (SAD#6.5); show the naive-fidelity label (SAD#2.7).
- **Avoid:** running a full-universe backtest in the browser thread.

### SAD#5.5 UI primitives — `ui/Spark.tsx`, `ui/Hoverable.tsx`
Sparkline (used by `whySpark` explainability) and hover affordances.
- **Use:** keep presentational and engine-agnostic.

### SAD#5.6 Catalogues & schemas
`INDICATOR_TYPES`, `IND_DEFAULTS`, `SOURCES`, `FIELDS`, `FLAGS`, `PATTERNS`,
`RANK_FIELDS`, `OP_LABELS`, `EMA_WINDOWS`, and the `PRESETS` library — the data
that drives builder UIs and the quick-signal toggles.
- **Use:** single source of truth for option lists and defaults; ported from the
  POC verbatim.
- **Avoid:** divergent copies in components or the server.

### SAD#5.7 Screening/backtest service handlers (SAD#4.2)
Thin HTTP handlers that load bars from SAD#5.10, invoke SAD#5.1
(`evalGroupedRules` / `backtestRules`) over the production universe, and return
JSON. Stateless w.r.t. user identity.
- **Use:** import the same engine module; stream/paginate large result sets;
  honour SAD#2.3/2.4 budgets; report backtest progress.
- **Avoid:** a second engine implementation; per-request recompute that ignores
  the indicator cache.

### SAD#5.8 Artifact repositories
Interface + implementation for persisting indicators, presets, and named
screens (SAD#6.4). One interface, swappable backing store (SAD#8 ADR-006).
- **Use:** all feature code reads/writes artifacts through this interface only.
- **Avoid:** components reaching into the storage mechanism directly.

### SAD#5.9 Client state store — `src/store.ts` (Zustand)
Holds the active rule set, current matches, last-screen snapshot (for the
SAD#3.9 diff banner), compare selection, and loaded artifacts.
- **Use:** the single client-side source of truth; selectors for derived views.
- **Avoid:** stashing engine functions or large bar arrays in global state
  unnecessarily.

### SAD#5.10 Market-data provider port + adapters (SAD#4.3)
`MarketDataProvider` interface returning adjusted OHLCV bars + universe metadata.
Adapters: a **synthetic adapter** (the POC generator, dev/test only — explicitly
not a product data source per SAD#1.2) and a **vendor adapter** (TBD,
SAD#8 ADR-008).
- **Use:** all bar access goes through the port; adjustment applied inside the
  adapter/ingestion (SAD#2.2).
- **Avoid:** the synthetic generator leaking into production code paths; engine
  code calling a provider directly (bars are passed in).

## SAD#6 Data

### SAD#6.1 Instrument & bars
Instrument: `ticker`, `name`, `sector`; daily OHLCV bars (**adjusted** for
splits/dividends before the engine sees them — SAD#2.2). Derived per instrument:
`price`, `changePct`, 52-week hi/lo, `pct52w` (range position), `relVol`.
- **Ownership:** market-data store (SAD#4.3). Read-only to the rest of the
  system. Adjustment is authoritative at ingestion.

### SAD#6.2 Indicator series & cache
Per-instrument scalar series: EMA(9/20/50/200 + arbitrary windows), RSI(14
Wilder), Stoch-RSI(%K/%D), MACD(line/signal/hist), volume SMA(20). Cached per
def keyed by a `defSig` signature.
- **Rule:** the cache is keyed by `defSig`; a def change must produce a new key.
  Cache is derived/ephemeral — never a source of truth.

### SAD#6.3 Indicator def
`{ type, source, length, fast, slow, signal, output, rsiLen, stochLen, kSmooth,
dSmooth }`; only keys relevant to `type` are read. This is a persisted artifact
(SAD#6.4).

### SAD#6.4 User-authored artifacts (persisted)
- **Indicator def** (SAD#6.3).
- **Preset:** `{ id, name, desc, rules[] }`.
- **Named screen:** `name` + chain/group.
- **Rules** carry kind (`num`/`flag`/`ema`/`ind`/`chain`/`group`/`pattern`/
  `rank`) and an optional `conj` (AND/OR). `ema`/`num`/`flag` are
  snapshot-based legacy kinds; `ind`/`chain`/`group` are the current path.
- **Ownership & access:** persisted behind SAD#5.8; the only mutable user data
  in the system. **Consistency:** last-write-wins within the single user;
  no cross-user reconciliation (single-tenant, SAD#1.2). Schema versioning of
  artifacts is required so future engine changes can migrate saved rules.

### SAD#6.5 Backtest result (transient)
`{ signals, evaluated, fireRate, horizons:[{ h, n, avg, median, winRate, best,
worst }] }`. Computed on demand by SAD#5.7; not persisted in v1 (display-only).
Carries the SAD#2.7 naive-fidelity label.

### SAD#6.6 Per-bar snapshots
Snapshot rows used for historical/per-bar evaluation and the `whySpark` trace.
Derived from bars + defs; ephemeral, never authoritative.

## SAD#7 Cross-cutting Concerns
- **Engine purity boundary:** SAD#2.6 is cross-cutting — any component importing
  the engine must pass data in and read results out; no I/O inside the engine.
- **Compliance disclosure:** SAD#2.7 — a shared disclosure component appears on
  every signal-bearing surface; backtest results always labelled naive in v1.
- **Config:** data-provider selection, API base URL, and feature flags are
  configuration, not code branches in feature components.
- **Error handling:** PCF parse failures and unsupported syntax surface
  explicit, user-readable errors (SAD#3.5) — never silently drop conditions.
- **Observability:** the screening service logs screen/backtest latency against
  the SAD#2.3/2.4 budgets so regressions are visible.
- **Auth:** none in v1 (SAD#1.2); the artifact repository interface (SAD#5.8) is
  shaped so a user-id dimension can be added without changing call sites.

## SAD#8 Decisions (ADRs)

### SAD#8.1 ADR-001: React + TS + Vite SPA is the product shell
- **Context:** the POC is a `dc-runtime` deckcode demo; the real app is
  scaffolded in `src/`.
- **Decision:** build the product as the React 19 + TypeScript + Vite SPA in
  `src/` with Zustand + react-router-dom + @tanstack/react-table. Drop
  `support.js`, `.dc.html`, `<x-dc>`, `sc-for`/`sc-if`, `data-dc-script`.
- **Consequences:** POC screens are rebuilt as React components (largely done);
  the deckcode harness is never carried forward (SAD#1.2).
- **Status:** accepted

### SAD#8.2 ADR-002: Port the engine verbatim as a pure isomorphic module
- **Context:** `market.js` is a dependency-free pure ES module carrying the
  trusted numeric semantics.
- **Decision:** port it to `src/lib/market.ts` preserving names and behaviour;
  add types only; pin with golden-master tests (SAD#2.1).
- **Consequences:** the engine runs unchanged in browser and Node, enabling
  ADR-003; numeric trust is protected by tests.
- **Status:** accepted

### SAD#8.3 ADR-003: Full-universe screen & backtest run server-side on the shared engine
- **Context:** browser-only compute works for 43 names, not thousands
  (SAD#2.5); the engine is isomorphic (ADR-002).
- **Decision:** a Node screening service (SAD#4.2) hosts the same engine for
  full-universe screens and backtests; the client computes only for displayed
  names (detail/compare/small sets).
- **Consequences:** introduces a client/server split and an HTTP/JSON contract;
  avoids forking the engine; meets SAD#2.3/2.4 budgets.
- **Status:** accepted

### SAD#8.4 ADR-004: Bars are passed into the engine, never fetched by it
- **Context:** engine purity (SAD#2.6).
- **Decision:** all data access goes through the `MarketDataProvider` port
  (SAD#5.10); callers pass bars into engine functions.
- **Consequences:** the engine stays testable and isomorphic; data sourcing is
  swappable.
- **Status:** accepted

### SAD#8.5 ADR-005: Corporate-action adjustment happens at ingestion
- **Context:** the engine assumes clean adjusted closes; the POC hides
  adjustment entirely (SAD#2.2).
- **Decision:** split/dividend adjustment is applied in the data layer
  (SAD#4.3/SAD#5.10) before bars reach the engine.
- **Consequences:** indicators and backtests are correct across corporate
  actions; the engine needs no adjustment logic.
- **Status:** accepted

### SAD#8.6 ADR-006: Persist artifacts behind a repository interface; defer the store
- **Context:** saved indicators/presets/screens are in-memory in the POC;
  accounts are out of scope but persistence is required (SAD#2.8).
- **Decision:** define one repository interface (SAD#5.8) now; choose the
  concrete backing store separately and keep a user-id dimension addable later.
- **Consequences:** feature code is insulated from the storage choice;
  accounts/auth can be introduced without rewriting call sites.
- **Status:** accepted

### SAD#8.7 ADR-007: Synthetic generator survives only as a dev/test adapter
- **Context:** the `mulberry32` universe is a demo fixture, not a feed
  (SAD#1.2).
- **Decision:** wrap it as a synthetic `MarketDataProvider` adapter for dev/test
  and golden-master fixtures only; never in a production path.
- **Consequences:** tests get deterministic data; production data is the
  vendor adapter (ADR-008).
- **Status:** accepted

### SAD#8.8 ADR-008: Market-data vendor selection (MVP interim decided; Yahoo & production deferred)
- **Context:** feed, coverage, EOD vs intraday, real-time vs delayed, adjustment
  method, and redistribution licensing are all undecided for **production**
  (PLAN-001 open questions; SAD#2.7). Two horizons are distinguished: the MVP
  (local, single-operator manual testing) and production (shipping data to users).
  An earlier interim (2026-07-08) made the **Yahoo** network importer the MVP boot
  default; that is **superseded** below — Yahoo is deferred to post-MVP.
- **Decision (MVP, interim — accepted):** the MVP data source is the existing
  **CSV importer** (`eod:import`, tools/eod-import, STORY-031) loading a **local,
  static EOD snapshot** into the SAD#6.1 `instrument`/`bar` schema, served by the
  SQLite adapter (STORY-032) behind the `MarketDataProvider` port (SAD#5.10). The
  snapshot in use is the Boris Marjanovic "Huge Stock Market Dataset" (Stooq-
  sourced, split/dividend-**adjusted** closes → `bar.c` at ingestion, SAD#2.2;
  ~7.2k US stocks + 1.3k ETFs through Nov 2017; ticker from the per-file stem).
  Scope is bounded to **local/personal use — the data is NOT redistributed.** No
  network fetch is on the MVP path; the DB is selected via `MARKETDATA_DB` / the
  dev pointer, else the synthetic generator (SAD#8.7). No **Yahoo boot-default
  tier** in server/universe.ts.
- **Decision (Yahoo) — *deferred to post-MVP.*** The Yahoo network fetcher
  (`yahoo:fetch`/`backfill`, tools/yahoo-fetch, STORY-050–053, PLAN-003) stays in
  the tree and working behind the port, but is **not a committed MVP data vendor**
  and is **not** the boot default. Rationale: the unofficial endpoint is rate-
  limited (hard HTTP 429 throttling observed from a dev IP, 2026-07-08) and its
  ToS bars redistribution — neither is worth carrying on the MVP critical path
  when a local static snapshot suffices. Re-selecting Yahoo (or any live vendor)
  is a fresh, explicit decision after MVP.
- **Decision (production) — *not yet made.*** Vendor selection **and**
  redistribution legal sign-off remain open and are a precondition to shipping
  data to real users. The port lets this stay deferred without blocking MVP work;
  v1 is daily/EOD (SAD#1.2). STORY-015 is the production adapter and stays blocked
  on this.
- **Consequences:** stories must target the port, not a vendor SDK. Ingesting the
  snapshot reuses the STORY-031 importer (the per-file layout needs only a small
  ingest config/`.txt` seam — no new write path). The production guard
  (server/universe.ts / STORY-033) still refuses ALL dev/test adapters —
  synthetic and SQLite — when `NODE_ENV=production`, so no dev dataset can back
  production traffic.
- **Status:** MVP interim accepted (local snapshot); Yahoo deferred; production
  proposed. (Yahoo-as-MVP interim of 2026-07-08 superseded 2026-07-09.)

### SAD#8.9 ADR-009: TC2000 PCF parity is a defined supported subset, not full coverage
- **Context:** full PCF-language coverage is explicitly out of scope (SAD#1.2);
  "paste any PCF" is an open question (PLAN-001).
- **Decision:** support exactly the POC `parsePCF` operator/indicator subset
  (XAVGC/AVGC, O·H·L·C·V, `.n` offsets, arithmetic, AND/OR, cross-overs);
  unsupported syntax fails loudly (SAD#3.5), never silently.
- **Consequences:** scope is bounded and testable; expanding the subset is a new,
  explicit decision.
- **Status:** accepted

### SAD#8.10 ADR-010: Backtest fidelity is naive in v1, labelled as such
- **Context:** the POC measures naive forward returns with no costs/slippage/
  sizing/significance (PLAN-001 open question; SAD#2.7).
- **Decision:** ship the POC's naive backtest in v1 with a persistent
  "illustrative, not an edge" label; defer rigor (costs/slippage/significance)
  to a later, explicit decision.
- **Consequences:** backtest is presentable without overclaiming; rigor work is
  a separate capability when committed.
- **Status:** accepted
