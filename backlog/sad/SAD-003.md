# Software Architecture Document — Yahoo Finance EOD market-data fetch

> **Status:** Reviewed
> **Version:** 0.1
> **This document is the binding architectural contract** for the EOD market-data
> fetch described in PLAN-003. Every story for this work references sections of
> this document by anchor (e.g. `SAD-003#5.1`). Implementation must not contradict
> an approved section. Conflicts are escalated, not improvised away.
>
> **Scope relationship to SAD-001:** this SAD *extends* the market-data ingestion
> boundary described in `SAD-001#4.3` / `SAD-001#5.10`; it does not supersede
> SAD-001. The system context, containers, engine, provider port, and SQLite
> schema of SAD-001 remain in force. This document **resolves the open vendor
> question** (`SAD-001#8.8 / ADR-008`) for a personal / dev-use deployment by
> selecting **Yahoo Finance EOD**, and adds the one missing link: a **network
> fetcher** that lands daily OHLCV in the existing `SAD-001#6.1` SQLite schema,
> where the existing `sqliteProvider` (STORY-032, `SAD-001#5.10`) already serves
> it through the `MarketDataProvider` port with **no engine, handler, or port
> change**. The two SAD-001 rules this work exists to honour are `SAD-001#2.2`
> (data correctness / adjustment at ingestion, `ADR-005`) and `SAD-001#2.7`
> (compliance / vendor-licence posture).

## Anchor convention

This document's anchors are written `SAD-003#<number>` (and
`SAD-003#<number>.<n>`). Cross-references to the system SAD use the explicit

## SAD-003#1 Context & Scope

The screener has no real market data. Production data today is either the
synthetic generator (a demo fixture, `SAD-001#8.7 / ADR-007`) or a SQLite DB
hand-fed from CSV files already on disk (the STORY-031 importer
`tools/eod-import` + the STORY-032 `sqliteProvider` reader). The vendor decision
(`SAD-001#8.8 / ADR-008`) is still **proposed**, so nothing actually *fetches*
real bars — a human has to source CSVs out-of-band.

The data layer is otherwise complete for this purpose. `tools/eod-import` parses
CSV → trusts bars as pre-adjusted (`SAD-001#2.2 / ADR-005`) → **idempotently
upserts** on `(ticker, date)` / `ticker` → writes the `instrument`/`bar` schema
(`SAD-001#6.1`, `tools/eod-import/db.ts`). It already ships `config.yahoo.json`
mapping the *shape* of a Yahoo/yfinance export (one file, a `Company` column, ISO
timestamped dates, ignored `Dividends`/`Stock Splits` columns). `sqliteProvider`
(`src/lib/data/sqlite.ts`) serves any such DB **read-only** through the
`SAD-001#5.10` port, opened read-only and validated at construction.

The single missing link is the **network fetch**: actually pulling Yahoo EOD
(historical backfill + a daily post-close update) and producing input for that
pipeline. This SAD adds exactly that link and makes Yahoo the named source for a
personal / non-redistributing deployment.

**System boundary:** unchanged from SAD-001. This work lives entirely in the
`SAD-001#4.3` ingestion boundary as a new Node/CLI tool and its tests; it adds no
container, no schema change, and no engine/handler/port edit. The fetcher is the
only new component; everything downstream of "bars on disk" is reused, not
rebuilt.

**Primary actor:** the operator (Mikael) running the screener for personal/dev
use — per the deployment decision, the *only* consumer. The screening service
(`SAD-001#4.2`) and web client (`SAD-001#4.1`) are downstream beneficiaries that
consume the resulting DB unchanged, not a new audience. No bars are redistributed
to third parties (`SAD-003#1.2`, `SAD-001#2.7`).

### SAD-003#1.1 In scope
- A **Yahoo EOD network fetcher** (Node/CLI, server-only) that pulls daily OHLCV
  for a supplied ticker universe: a **historical backfill** and a **daily
  post-close append**.
- **Normalisation** of the Yahoo response into the existing importer's input,
  so `tools/eod-import` + `config.yahoo.json` write the `SAD-001#6.1` schema
  unchanged (`SAD-003#3.2`, `SAD-003#8.2 / ADR-002`).
- **Adjusted-close mapping:** the engine-visible close (`bar.c`) is Yahoo's
  `adjClose`, honouring `SAD-001#2.2 / ADR-005` (`SAD-003#6.1`,
  `SAD-003#8.4 / ADR-004`).
- **Coverage & freshness reporting** per run, plus an explicit partial-failure
  policy (`SAD-003#3.3`, `SAD-003#8.5 / ADR-005`).
- The **`SAD-001 ADR-008` flip**: Yahoo Finance EOD accepted as the data source,
  **scoped to non-redistribution** (`SAD-003#8.1 / ADR-001`).
- **Data-source selection:** the Yahoo-sourced DB is a distinct file, selectable
  through the existing `MARKETDATA_DB` / TopBar data-source path alongside the
  synthetic generator (`SAD-003#6.2`).

### SAD-003#1.2 Out of scope (non-goals)
> This list is a primary scope-creep defense. A story that builds something here
> is invalid by definition. Carried verbatim from PLAN-003.

- **No intraday / real-time / streaming.** EOD daily bars only (`SAD-001#1.2`
  reaffirmed). No tick, minute, or delayed-quote feeds.
- **No redistribution / no external serving / no accounts.** Bars stay on the
  operator's machine. Multi-tenant or product serving of Yahoo data is OUT and
  would require re-opening `ADR-008`. This keeps the deployment inside Yahoo's
  ToS.
- **No full OHLC corporate-action back-adjustment.** Only `adjClose` is used this
  plan. Deriving adjusted open/high/low/volume from split/dividend events is a
  deferred follow-on, not built here.
- **No vendor-agnostic ingestion framework.** One Yahoo fetcher. The port
  (`SAD-001#5.10`) already provides swappability; building a pluggable
  multi-vendor abstraction is OUT.
- **No new SQLite schema or store redesign.** Reuse STORY-031's `instrument`/
  `bar` schema (`SAD-001#6.1`) and STORY-032's reader verbatim.
- **No engine, rule-semantics, or client changes.** This is data-layer-only work
  upstream of the port. If a story here touches `market.ts` or a component, it
  has left scope.
- **No fundamentals / financials / news / corporate-actions product data.**
  OHLCV + universe metadata (ticker/name/sector) only. (Split/dividend *events*
  may be *stored* for later adjustment — see Open questions — but are not a
  product surface, per `SAD-001#1.2`.)
- **No live runtime Yahoo provider.** No fetching at request time, no making the
  port async. Ingestion-to-DB only; the synchronous port is untouched.
- **No universe-discovery / index-membership service.** The set of tickers is a
  supplied list (config/file); computing index constituents is OUT.
- **No scheduling infrastructure.** The daily run is invoked by an external
  trigger (cron / manual / a separate scheduling concern); building a scheduler
  is OUT of this plan.

## SAD-003#2 Quality Attributes & Constraints

Each attribute is phrased so a story can be checked against it.

### SAD-003#2.1 Reuse without modification (highest priority)
The Yahoo path must serve through the **existing** data layer with **zero
changes** to `src/lib/data/provider.ts`, `src/lib/data/sqlite.ts`, the engine
(`src/lib/market.ts`), or the screening/backtest handlers (`SAD-001#5.7`).
**Posture:** a backfill writes a SQLite DB that `sqliteProvider` opens and serves,
and the app/screen runs against the Yahoo DB **exactly** as it runs against
synthetic — verified by pointing `MARKETDATA_DB` at the Yahoo DB with no other
edit. Any diff to those files is out of scope by definition (`SAD-003#1.2`).

### SAD-003#2.2 Idempotent daily append
A post-close run appends the latest bar(s); **re-running the same day produces no
duplicate rows.** **Posture:** the run reuses the importer's
`ON CONFLICT(ticker, date)` upsert (`tools/eod-import/db.ts`); a test runs the
daily append twice and asserts row counts are unchanged on the second run and
bar values are overwritten in place, not duplicated.

### SAD-003#2.3 Adjusted close reaches the engine
The close the engine sees (`bar.c`) is Yahoo's `adjClose`, so split/dividend-
spanning windows are correct on close, and **no** adjustment math enters the
engine (`SAD-001#2.2 / 2.6`, `ADR-005`). **Posture:** a fixture spanning a known
split asserts `bar.c` equals the source `adjClose`, not the raw `close`; an
inspection confirms no corporate-action arithmetic exists in the fetcher or the
engine (`SAD-003#8.4 / ADR-004`).

### SAD-003#2.4 Coverage & freshness are reportable per run
Every run reports **(a)** the % of the target universe fetched successfully and
**(b)** max staleness — newest bar date vs the last trading day after a daily
run. **A run that silently drops names is a failure.** **Posture:** the run emits
a structured report listing every requested ticker as fetched/failed with a
reason; a run that falls below a configured coverage threshold exits non-zero
(`SAD-003#8.5 / ADR-005`).

### SAD-003#2.5 Server/CLI-only; no secret leak into the client
The fetcher is server/CLI-only and **never enters the client bundle** (mirrors
the STORY-032 `node:sqlite` constraint, `src/lib/data/sqlite.ts`). No secret or
credential is checked in, and no third-party **runtime** dependency is added
beyond what the fetch itself requires. **Posture:** the fetcher module imports
nothing that the client bundle pulls in; a guard asserts the client build does
not reference it; the repo carries no API key/token.

### SAD-003#2.6 Engine purity preserved (inherited, non-negotiable)
The fetcher is a Node/CLI ingestion tool; bars are passed into the engine via the
port (`SAD-001#2.6 / 8.4 / ADR-004`). **Rule:** no DOM/`fetch`/network in the
engine, and no "today" leaking in; all network I/O lives in the fetcher.
**Posture:** the engine module is unchanged and the engine-purity guard still
passes.

### SAD-003#2.7 Politeness against an unofficial endpoint
The fetcher hits an unofficial Yahoo endpoint; it must not abuse it. **Rule:** a
bounded request rate (configurable batch size + inter-request delay) and
retry/backoff on transient failures, so a backfill does not risk IP throttling.
**Posture:** the fetch loop has a configurable delay and a bounded retry/backoff;
a test asserts the backoff path on a simulated transient error (`SAD-003#2.4`
covers the give-up/report path).

## SAD-003#3 Capabilities

Capabilities are the unit of work for the build loop. Each has a stable id and an
explicit acceptance posture. These are **ingestion-boundary** capabilities
(`SAD-001#4.3`) that feed, and are consumed unchanged by, the SAD-001 product
capabilities.

### SAD-003#3.1 CAP-eod-fetch: Yahoo EOD network fetcher
- **What it does:** fetches daily OHLCV (raw `open/high/low/close/volume` plus
  `adjClose`) for a supplied ticker over a date range from the Yahoo v8 `chart`
  JSON endpoint (`SAD-003#8.3 / ADR-003`), with bounded politeness/backoff
  (`SAD-003#2.7`). Two modes: a **historical backfill** (range/depth) and a
  **daily post-close append** (since last stored bar).
- **Primary components:** `SAD-003#5.1`.
- **Acceptance posture:** for a recorded fixture response, the fetcher yields the
  expected normalised rows for a known ticker/date range, including `adjClose`
  distinct from raw `close`; transient failures retry then surface (no silent
  drop, `SAD-003#2.4`). No live network call runs in CI (`SAD-003#8.6 / ADR-006`).

### SAD-003#3.2 CAP-eod-ingest: Fetch → existing importer → SQLite DB
- **What it does:** normalises fetched bars into the importer's CSV input shape
  and runs `tools/eod-import` + `config.yahoo.json` to land them in the
  `SAD-001#6.1` schema, idempotently (`SAD-003#2.2`). Reuses the importer's
  parse/upsert + metadata-resolution path rather than re-implementing DB writing
  (`SAD-003#8.2 / ADR-002`).
- **Primary components:** `SAD-003#5.1`, `SAD-003#5.2`, and the **reused**
  `tools/eod-import` (STORY-031) + `sqliteProvider` (STORY-032, `SAD-001#5.10`).
- **Acceptance posture:** a backfill over a supplied ticker list writes a SQLite
  DB that `sqliteProvider` opens and serves with **zero changes** to
  `provider.ts` / `sqlite.ts` / the engine; the app/screen runs against the
  Yahoo DB exactly as against synthetic (`SAD-003#2.1`). A second same-day run
  adds no duplicate rows (`SAD-003#2.2`).

### SAD-003#3.3 CAP-eod-coverage: Coverage & freshness reporting + partial-failure policy
- **What it does:** produces a per-run report of universe coverage (% fetched)
  and freshness (newest-bar vs last-trading-day staleness); on partial failure it
  **commits the successful set** and reports failures loudly, exiting non-zero
  below a configured coverage threshold (`SAD-003#8.5 / ADR-005`).
- **Primary components:** `SAD-003#5.3`.
- **Acceptance posture:** a run with some tickers failing commits the rest and
  emits a report naming every failure with a reason; coverage and max-staleness
  are present and correct in the report; the run's exit code reflects the
  threshold. A silently-dropped name is a test failure (`SAD-003#2.4`).

## SAD-003#4 Containers

No new or changed containers. All work lives inside the existing **market-data
ingestion boundary** (`SAD-001#4.3`) as a Node/CLI tool alongside
`tools/eod-import`, and is consumed by the existing **screening service**
(`SAD-001#4.2`) and **web client** (`SAD-001#4.1`) through the unchanged
`MarketDataProvider` port (`SAD-001#5.10`). The fetcher is server/CLI-only and
must never enter the client bundle (`SAD-003#2.5`). The Yahoo-sourced SQLite DB
is a distinct file within the `SAD-001#4.3` store, selectable via `MARKETDATA_DB`
(`SAD-003#6.2`).

## SAD-003#5 Components

Patterns to use and to avoid are called out because stories cite this section
most.

### SAD-003#5.1 Yahoo EOD fetcher — new Node/CLI tool (e.g. `tools/yahoo-fetch/`)
The network front-end: given a ticker universe + a mode (backfill range / daily
since-last), it calls the Yahoo v8 `chart` JSON endpoint, parses the response
into normalised daily rows (`date, open, high, low, close, adjClose, volume`),
and applies politeness/backoff (`SAD-003#2.7`). Uses Node's built-in `fetch`
(`SAD-003#8.3 / ADR-003`).
- **Use:** keep all network I/O here; make HTTP injectable so tests use recorded
  fixtures (`SAD-003#8.6 / ADR-006`); structure it like `tools/eod-import`
  (pure parse/normalise functions + a thin CLI doing I/O); server/CLI-only,
  never imported by client code (`SAD-003#2.5`); honour a configurable delay,
  batch size, and retry/backoff.
- **Avoid:** adding a third-party Yahoo wrapper as a runtime dependency
  (`SAD-003#2.5`); doing any corporate-action arithmetic here (`SAD-003#2.3`);
  fetching at request time or inside the engine (`SAD-001#1.2`, `SAD-003#2.6`);
  swallowing a failed ticker without reporting it (`SAD-003#2.4`).

### SAD-003#5.2 Fetch → import seam — normaliser to the importer's input
The normalisation that turns fetched rows into what `tools/eod-import` consumes,
reusing `config.yahoo.json` (`Company` ticker column, `iso` dates, ignored
`Dividends`/`Stock Splits`). Per `ADR-002` the fetcher **emits the importer's CSV
input** and invokes the existing importer, rather than calling `db.ts` directly.
- **Use:** map `adjClose` → the importer's close column so `bar.c` is the
  adjusted close (`SAD-003#6.1`, `SAD-003#8.4 / ADR-004`); reuse the importer's
  metadata-resolution precedence (CSV → metadata file → default) for name/sector;
  keep the seam a thin, tested normaliser.
- **Avoid:** a second DB-writing path that bypasses the importer's idempotent
  upsert (`SAD-003#2.2`); re-mapping columns in a way that diverges from
  `config.yahoo.json`; forking the importer.

### SAD-003#5.3 Coverage & freshness reporter
Aggregates per-ticker fetch outcomes into the `SAD-003#2.4` report (coverage %,
max staleness, per-ticker failures with reasons) and enforces the partial-failure
policy / threshold exit (`SAD-003#8.5 / ADR-005`).
- **Use:** treat the report as a first-class run output (structured + printable);
  derive freshness from the newest written bar date vs the last trading day;
  drive the non-zero exit from a configurable coverage threshold.
- **Avoid:** burying failures in logs only; reporting an aggregate that hides
  which names were dropped.

### SAD-003#5.4 Reused, unchanged — importer (STORY-031) & sqliteProvider (STORY-032)
`tools/eod-import` (`parse.ts` / `db.ts` / `run.ts`, the `instrument`/`bar`
schema) and `src/lib/data/sqlite.ts` (the `SAD-001#5.10` read adapter, opened
read-only and validated at construction). **These are consumed verbatim** — the
Yahoo path produces input for them and a DB served by them.
- **Use:** depend on their existing public surfaces (`runImport`,
  `EodDatabase.write`'s upsert, the provider's `getUniverse`/`getInstrument`);
  point `MARKETDATA_DB` at the Yahoo DB.
- **Avoid:** editing `provider.ts` / `sqlite.ts` / `market.ts` / the handlers
  (`SAD-003#2.1`); changing the importer's schema or upsert semantics
  (`SAD-003#1.2`).

## SAD-003#6 Data

### SAD-003#6.1 No schema change — column mapping into `instrument`/`bar`
Reuse the STORY-031 schema verbatim (`SAD-001#6.1`, `tools/eod-import/db.ts`):
`instrument(ticker, name, sector)` and `bar(ticker, date, o, h, l, c, v)` keyed
on `(ticker, date)`. The Yahoo response maps as:
- **`c` ← Yahoo `adjClose`** (the engine-visible adjusted close, `SAD-003#2.3`,
  `ADR-005`).
- **`o`, `h`, `l` ← raw open/high/low**, **`v` ← raw volume**, **`date` ← the
  bar's trading date** (ISO, the `iso` `dateFormat`).
- **Rule:** because the schema carries a single `c`, **only the close is
  adjusted**; `o/h/l` remain raw. This is a **known, documented limitation** —
  OHL are not back-adjusted across splits, so candlestick OHL across a split
  boundary can show pre-adjustment artifacts while *close-based* indicators are
  correct. Full per-OHLC back-adjustment is the deferred follow-on
  (`SAD-003#6.3`, `SAD-003#1.2`, `SAD-003#8.4 / ADR-004`). No corporate-action
  arithmetic is performed in this scope.
- **Ownership:** the market-data store (`SAD-001#4.3`), read-only to the rest of
  the system; the fetcher's import run is the only writer of the Yahoo DB.

### SAD-003#6.2 Yahoo DB file lifecycle & selection
The Yahoo-sourced DB is a **distinct SQLite file**, separate from the synthetic
generator's data and from golden-master fixtures (`SAD-001#8.7 / ADR-007`):
synthetic stays the deterministic test fixture; the Yahoo DB is real-but-personal
data. It is selected via the existing `MARKETDATA_DB` / TopBar data-source path
(`SAD-001#5.2` shell), with no new selection mechanism.
- **Rule:** a stable, documented path/naming convention for the Yahoo DB;
  re-running backfill/append against the same file is idempotent (`SAD-003#2.2`).
- **Avoid:** writing the Yahoo DB over the synthetic/golden fixtures; introducing
  a new data-source selector when `MARKETDATA_DB` already exists.

### SAD-003#6.3 Reserved (not built) — raw OHLCV + corporate-action events
The deferred full-OHLC back-adjustment (`SAD-003#1.2`) would require persisting
**both** raw OHLCV and `adjClose` (and split/dividend events) so adjusted
open/high/low/volume can be derived without re-fetching. That is a **separate,
explicit future decision** with its own schema change; it is **not** built here
and must not be smuggled into this scope. This SAD stores only what
`SAD-003#6.1` defines.

## SAD-003#7 Cross-cutting Concerns
- **Reuse boundary:** `SAD-003#2.1` is cross-cutting — every story keeps
  `provider.ts` / `sqlite.ts` / `market.ts` / the handlers untouched; the Yahoo
  path only adds the fetcher and produces input/DB for the existing layer.
- **Adjustment trust:** `ADR-005` adjustment-at-ingestion is honoured by trusting
  the source `adjClose` (`SAD-003#2.3`); no component re-derives adjustment.
- **Coverage discipline:** the per-run coverage/freshness report (`SAD-003#5.3`)
  is the contract that "a run that silently drops names is a failure" —
  cross-cutting across fetch and ingest.
- **Server-only boundary:** `SAD-003#2.5` — the fetcher (like `node:sqlite`
  consumers) must never enter the client bundle; the build guard spans every
  fetcher module.
- **Compliance posture:** `SAD-001#2.7` — the non-redistribution scope
  (`SAD-003#8.1 / ADR-001`) is the licence guardrail; serving Yahoo data beyond
  the operator's machine re-opens `ADR-008`.
- **Testability:** recorded HTTP fixtures (`ADR-006`) keep the suite deterministic
  against an unstable external endpoint, the same discipline the importer already
  uses for its parse/upsert fixtures.

## SAD-003#8 Decisions (ADRs)

### SAD-003#8.1 ADR-001: Select Yahoo Finance EOD, scoped to non-redistribution (flips SAD-001 ADR-008)
- **Context:** the SAD-001 vendor decision (`SAD-001#8.8 / ADR-008`) is *proposed*;
  for a personal/dev deployment the cost-free Yahoo unofficial EOD endpoint is
  sufficient, but its ToS prohibits commercial redistribution (`SAD-001#2.7`).
- **Decision:** flip `SAD-001 ADR-008` **proposed → accepted, scoped to
  non-redistribution**: Yahoo Finance EOD is the data source **for a
  personal/non-redistributing deployment only**. Bars are never served to third
  parties (`SAD-003#1.2`). A redistributable deployment re-opens `ADR-008` for a
  licensed vendor (the existing STORY-015 placeholder).
- **Consequences:** real EOD data lands without a paid licence; the deployment is
  bound to the operator's machine; the licensed-vendor path remains open and
  unbuilt. `SAD-001#2.7` disclosure is honoured.
- **Status:** accepted

### SAD-003#8.2 ADR-002: Fetcher emits the importer's CSV input; reuse `tools/eod-import`
- **Context:** PLAN-003 open question — does the fetcher emit a CSV the existing
  importer consumes, or call the importer's `db.ts` writer directly? The importer
  already provides idempotent upsert + `config.yahoo.json` column mapping.
- **Decision:** the fetcher **normalises to the importer's CSV input** and runs
  `tools/eod-import` + `config.yahoo.json`; it does **not** call `db.ts` directly.
- **Consequences:** maximal reuse and a clean fetch/ingest separation; one
  idempotent write path (`SAD-003#2.2`); the fetch front-end stays decoupled from
  the DB writer. A modest extra normalise-to-CSV step is accepted as the cost.
- **Status:** accepted

### SAD-003#8.3 ADR-003: Access via the Yahoo v8 `chart` JSON endpoint using built-in `fetch`
- **Context:** PLAN-003 open question — v8 `chart` JSON API vs the (retired) CSV
  `download` endpoint vs a wrapper like `yahoo-finance2`. The constraint is
  server/CLI-only and no new runtime dependency beyond what the fetch requires
  (`SAD-003#2.5`).
- **Decision:** fetch from the Yahoo **v8 `chart` JSON endpoint** using Node's
  built-in `fetch`; **no third-party Yahoo wrapper** as a runtime dependency. The
  `chart` response carries raw OHLCV and an `adjclose` series directly.
- **Consequences:** no new runtime dep; full control over politeness/backoff
  (`SAD-003#2.7`); coupled to an unofficial, unstable endpoint whose response
  shape may change — mitigated by recorded fixtures (`ADR-006`) and the coverage
  report (`SAD-003#2.4`). Revisiting the wrapper is a later, explicit decision.
- **Status:** accepted

### SAD-003#8.4 ADR-004: Trust `adjClose` as the engine-visible close; defer full-OHLC adjustment
- **Context:** the engine assumes clean adjusted closes (`SAD-001#2.2 / ADR-005`);
  the `SAD-001#6.1` schema carries a single `c`. PLAN-003 open question — store
  only adjusted close, or persist raw OHLCV + events too?
- **Decision:** map **`bar.c` ← Yahoo `adjClose`**, leave `o/h/l/v` raw, and
  perform **no** corporate-action math (`SAD-003#6.1`). Persisting raw + events
  for full per-OHLC back-adjustment is a **deferred follow-on** (`SAD-003#6.3`),
  not built here.
- **Consequences:** close-based indicators are correct across splits with no
  engine change; OHL are **not** back-adjusted — a documented limitation
  (`SAD-003#6.1`) visible only on raw OHL candlesticks across a split boundary.
  No schema change in this scope; the follow-on is a separate decision.
- **Status:** accepted

### SAD-003#8.5 ADR-005: Partial-failure → commit the partial set + mandatory coverage report
- **Context:** PLAN-003 open question — on partial failure, commit the partial
  set or fail the whole run? The coverage metric forbids silently dropping names
  (`SAD-003#2.4`).
- **Decision:** **commit the successfully-fetched set** and emit a mandatory
  coverage/freshness report naming every failure with a reason; the run exits
  **non-zero** when coverage falls below a configured threshold.
- **Consequences:** a transient failure on a few tickers does not discard a whole
  backfill; failures are always visible; CI/automation can gate on the exit code.
  Silent partial success is impossible by construction.
- **Status:** accepted

### SAD-003#8.6 ADR-006: Tests use recorded HTTP fixtures; no live network in CI
- **Context:** PLAN-003 open question — recorded fixtures vs live calls, given the
  fetcher hits an external, unstable endpoint. The importer already fixture-tests
  its parse/upsert.
- **Decision:** make the HTTP layer injectable and test the fetcher against
  **recorded Yahoo responses**; **no live network call runs in CI**.
- **Consequences:** the suite is deterministic and offline; endpoint drift is
  caught by refreshing fixtures, not by flaky CI; an optional manual live-smoke
  path can exist outside CI.
- **Status:** accepted

### SAD-003#8.7 ADR-007: Reuse `sqliteProvider` as the serving path; widen its scope to dev/test/personal
- **Context:** `sqliteProvider` (STORY-032, `src/lib/data/sqlite.ts`) is scoped
  "DEV/TEST ONLY" under `SAD-001#8.7 / ADR-007`; PLAN-003 reuses it to serve real
  (but personal) Yahoo data and does **not** add a new `SAD-001#5.10` read
  adapter.
- **Decision:** serve the Yahoo DB through the **existing** `sqliteProvider`
  unchanged; **widen its scope from "dev/test fixtures" to "dev/test/personal
  data"**, still explicitly **not** a redistributing product adapter. The
  licensed-vendor adapter (STORY-015) remains the path for a redistributable
  product (`ADR-001`).
- **Consequences:** no new read adapter, no port change, no `provider.ts`/
  `sqlite.ts` edit (`SAD-003#2.1`); the "Yahoo adapter" is the **ingestion
  fetcher** at `SAD-001#4.3`, not a new `SAD-001#5.10` adapter. The non-
  redistribution boundary (`ADR-001`) is what keeps this consistent with
  `SAD-001#2.7`.
- **Status:** accepted

### SAD-003#8.8 ADR-008: No scheduler; the daily run is externally triggered, idempotent re-run is resumability
- **Context:** PLAN-003 open question — daily-run trigger and backfill
  resumability; scheduling infrastructure is a non-goal (`SAD-003#1.2`).
- **Decision:** the daily post-close append is invoked by an **external trigger**
  (cron / manual); the tool builds **no scheduler**. Resumability is provided by
  **idempotent upsert** (`SAD-003#2.2`): an interrupted or partial backfill is
  recovered by simply re-running, which overwrites in place and adds no
  duplicates.
- **Consequences:** the tool stays a single-shot CLI; operations decide the
  trigger; no resume bookkeeping/state file is needed because re-running is safe.
  A smarter "fetch only since last stored bar" optimisation is an efficiency
  refinement within the daily mode, not a separate resume mechanism.
- **Status:** accepted
