# Software Architecture Document — Layered Indicator Calculus (computation DAG)

> **Status:** Draft
> **Version:** 0.1
> **This document is the binding architectural contract** for the indicator-engine
> refactor described in PLAN-002. Every story for this work references sections of
> this document by anchor (e.g. `SAD-002#6.1`). Implementation must not contradict
> an approved section. Conflicts are escalated, not improvised away.
>
> **Scope relationship to SAD-001:** this SAD *extends* the engine described in
> `SAD-001#5.1`; it does not supersede SAD-001. The system context, containers,
> data ownership, and all product capabilities of SAD-001 remain in force. This
> document deepens the **internal structure of the engine** and adds engine-level
> capabilities. The two SAD-001 rules this refactor exists to honour are
> `SAD-001#2.1` (numeric fidelity) and `SAD-001#2.6` (engine purity).

## Anchor convention

This document's anchors are written `SAD-002#<number>` (and `SAD-002#<number>.<n>`).
Cross-references to the system SAD use the explicit `SAD-001#<number>` form, since
two SADs now coexist and `sad_refs` must be unambiguous. **Never renumber an anchor
once stories reference it** — append instead. Capability ids (`CAP-dag-*`) are
globally unique regardless of document.

## SAD-002#1 Context & Scope

The engine in `src/lib/market.ts` (`SAD-001#5.1`) computes every indicator as a
flat scalar series cached per def (`indSeries` keyed by `defSig`), with **no model
of what depends on what**. This refactor restructures that engine into an explicit
**computation DAG**: raw OHLCV at the root, every indicator declaring its inputs,
and *level* derived as topological depth (`level = 1 + max(level of inputs)`; raw
sources are level 0). The DAG is plain data, evaluated by a topological, memoising
evaluator that computes each node once per instrument-bar and only when reachable
from a rule.

The **primary driver is scalability** (`SAD-001#2.5`): an explicit dependency graph
is the structure the screening service (`SAD-001#4.2`) needs to schedule, share,
and prune computation. Reuse (single source of truth per node) and richer
composition (algebraic/relational/pattern nodes) are secondary wins captured here;
**authoring UX and the actual server-side materialisation are explicitly out**, as
is the **temporal sequencing layer** (deferred to a follow-on — see SAD-002#1.2).

**System boundary:** unchanged from SAD-001. This refactor lives entirely inside
the pure engine module and its tests; it adds no container, no I/O, and no
persisted-schema change.

### SAD-002#1.1 In scope
- A node/expression-graph data model for indicators, with **derived levels** and
  raw OHLCV as the ground level.
- **Lowering** of the existing indicators (`ema`/`sma`/`rsi`/`macd`/`stochrsi`) and
  rule operands (`group`/`chain`/`cond`, `×mult/+add`) into DAG nodes.
- A topological, **memoising evaluator** keyed by node identity, replacing the
  per-`defSig` cache; prunable (touches only a rule's transitive inputs) and
  schedulable (topological order is addressable).
- First-class **algebraic** combinator nodes (`+ − × ÷`) and **relational/boolean**
  nodes (`> < ≥ ≤ == !=`, `cross_up`/`cross_down`).
- **Price-action patterns** (`SAD-001#3.7`) expressed as boolean DAG nodes.
- A **backward-compatible public surface**: existing `indSeries`, the `eval*` rule
  functions, `PRESETS`, the builder catalogues, and PCF lowering keep working so
  consuming components (`SAD-001#5.2/5.3/5.4`) and the store (`SAD-001#5.9`) are
  unchanged.
- A **differential fidelity harness** proving the new engine reproduces the current
  engine bar-for-bar.

### SAD-002#1.2 Out of scope (non-goals)
> This list is a primary scope-creep defense. A story that builds something here is
> invalid by definition. Carried verbatim from PLAN-002.

- **Temporal sequencing is OUT of this plan.** No `THEN` / `WITHIN n bars` /
  `WHILE … never …` / onset-edge / Allen-style interval operators, and no per-setup
  state machine. The per-bar evaluation model is unchanged. Temporal algebra is a
  deliberate follow-on idea that builds *on top of* this DAG once it exists —
  capturing it here would multiply scope and architectural risk.
- **No new indicator math.** This plan adds no new indicator *types*; it
  restructures how the existing ones are computed and composed. (Algebraic and
  relational *combinator* nodes are in scope as composition primitives, but they
  combine existing series — they are not new indicators.)
- **No greenfield replacement.** The current flat engine is not thrown away and
  rewritten from scratch; it is refactored in place with the old path preserved
  until parity is proven.
- **No authoring-UX overhaul in this plan.** Surfacing DAG-composition in the
  indicator/setup builders (`SAD-001#3.3/3.4`) and DAG-walking explainability
  (`SAD-001#3.10`) are downstream once the model lands — not part of the core
  refactor.
- **No server/materialisation implementation here.** This plan makes computation
  *schedulable* (the DAG + clean evaluation contract); actually moving it to the
  screening service or a precompute store is the `SAD-001#2.5` follow-through, not
  this scope.
- **No change to backtest semantics (`SAD-001#3.11`)** beyond preserving identical
  results — sequenced-setup backtest semantics ride with the temporal follow-on.

## SAD-002#2 Quality Attributes & Constraints

Each attribute is phrased so a story can be checked against it.

### SAD-002#2.1 Numeric fidelity (highest priority)
The refactored engine reproduces the current `src/lib/market.ts` output
**bar-for-bar** over the existing golden-master fixtures (`SAD-001#2.1`).
**Posture:** a differential harness (SAD-002#5.5) evaluates old vs new engine over
the fixture universe for every indicator type, every preset in `PRESETS`, and the
PCF example; **any divergence fails CI**. This is the gate, not a target.

### SAD-002#2.2 Engine purity (inherited, non-negotiable)
The DAG is plain data; the engine stays a dependency-free, side-effect-free,
isomorphic ES module (`SAD-001#2.6`). **Rule:** no DOM, no `fetch`, no global state,
no "today" inside the engine; bars passed in (`SAD-001#8.4 / ADR-004`).
**Posture:** the engine module imports nothing from React/DOM/Node; a lint/test
guard asserts it.

### SAD-002#2.3 Backward compatibility of the public surface
Existing exported functions (`indSeries`, `evalRuleAt`, `evalGroupedRules`,
`evalGroupAt`, `evalCondAt`, `evalChainAt`, `evalIndRuleAt`, `evalPatternAt`,
`rankPassSet`, `parsePCF`, `backtestRules`), the `PRESETS` library, and the
catalogues (`SAD-001#5.6`) keep their signatures and behaviour.
**Posture:** the entire existing engine + component test suite passes unchanged; no
consuming component (`SAD-001#5.2/5.3/5.4`) or the store (`SAD-001#5.9`) is edited
to accommodate the refactor.

### SAD-002#2.4 Schedulability & prunability
The DAG is topologically orderable, and evaluating a rule touches **only its
transitive input nodes**. A node shared by multiple rules/indicators is computed
**once per instrument-bar**; a catalogued-but-unreferenced node is **never**
computed. **Posture:** a node-evaluation counter shows (a) shared sub-expressions
computed once, and (b) zero evaluations for unreferenced nodes, over a fixture
screen.

### SAD-002#2.5 No latency regression
Full-universe screening latency must not regress beyond the `SAD-001#2.3` budget
(p95 ≤ 3 s warm-cache); single-name detail re-eval stays ≤ 50 ms. **Posture:** a
benchmark over the fixture universe shows new ≤ old within tolerance; dedup of
shared sub-expressions should make it ≤, not >.

### SAD-002#2.6 Derived-level invariant
A node's level is **computed**, never hand-assigned: raw sources are level 0; every
other node is `1 + max(level of its inputs)`. **Posture:** a test asserts known
nodes resolve to expected levels (e.g. `ema`=1, `macd`=2, `relVol`=2) and that the
graph is acyclic.

### SAD-002#2.7 Bounded, correctly-invalidated cache
Per-(instrument, node) memoisation is derived/ephemeral and never a source of truth
(`SAD-001#6.2`). Adding a custom EMA window (`ensureEma`) or a new node must not
return stale series, and the cache must not grow unbounded across a large universe.
**Posture:** a test adds a node after first evaluation and confirms a correct,
non-stale series; cache keys are node identities (SAD-002#6.1), so a changed node
yields a new key.

## SAD-002#3 Capabilities

Capabilities are the unit of work for the build loop. Each has a stable id and an
explicit acceptance posture. These are **engine-internal** capabilities that
extend, and are consumed by, the SAD-001 product capabilities.

### SAD-002#3.1 CAP-dag-model: Node/expression graph data model
- **What it does:** defines the node data structure (kind, inputs, params/op) and
  the node-kind taxonomy (raw-source, aggregation, composite, algebraic,
  relational, pattern); level is derived (SAD-002#2.6).
- **Primary components:** SAD-002#5.1.
- **Acceptance posture:** node levels resolve as expected, the graph is asserted
  acyclic, and node identity (SAD-002#6.1) is stable for equal nodes and distinct
  for different ones.

### SAD-002#3.2 CAP-dag-lower: Lowering existing indicators & rules into the DAG
- **What it does:** maps each existing `IndicatorDef` (`ema`/`sma`/`rsi`/`macd`/
  `stochrsi`/`price`) and rule operand (`group`/`chain`/`cond`, with `×mult/+add`,
  bar offsets) onto DAG nodes; PCF output (`SAD-001#3.5`) lowers through the same
  path.
- **Primary components:** SAD-002#5.3, SAD-002#5.1.
- **Acceptance posture:** every indicator type and every `PRESETS` entry lowers to
  a DAG that evaluates **bar-for-bar identical** to the current engine
  (SAD-002#2.1); bar offsets and arithmetic are preserved exactly.

### SAD-002#3.3 CAP-dag-eval: Topological memoising evaluator
- **What it does:** evaluates a node (and its transitive inputs) over an
  instrument's bars in topological order, memoising per (instrument, node);
  replaces the per-`defSig` cache while preserving `indSeries` results.
- **Primary components:** SAD-002#5.2, SAD-002#5.6.
- **Acceptance posture:** results equal the old cache's series (SAD-002#2.1); shared
  sub-expressions computed once and unreferenced nodes never computed
  (SAD-002#2.4); no latency regression (SAD-002#2.5); correct invalidation
  (SAD-002#2.7).

### SAD-002#3.4 CAP-algebra: Algebraic combinator nodes
- **What it does:** first-class `+ − × ÷` nodes that combine scalar series; the
  existing per-operand `×mult/+add` and `hl2`/`hlc3`-style derivations lower into
  these.
- **Primary components:** SAD-002#5.1, SAD-002#5.3.
- **Acceptance posture:** an expression like `(EMA18 − EMA50) / ATR-substitute`
  evaluates correctly; existing `×mult/+add` operands produce **identical** results
  after lowering (SAD-002#2.1).

### SAD-002#3.5 CAP-relational: Relational / boolean nodes
- **What it does:** `> < ≥ ≤ == !=` and `cross_up`/`cross_down` as boolean nodes
  that consume scalar nodes; the existing comparison operators in `cond`/`chain`/
  `ind` rules lower into these.
- **Primary components:** SAD-002#5.1, SAD-002#5.3.
- **Acceptance posture:** every comparison/cross operator reproduces the POC truth
  values bar-for-bar (`evalCondAt`/`evalChainAt`/`evalIndRuleAt` parity).

### SAD-002#3.6 CAP-pattern-nodes: Price-action patterns as DAG nodes
- **What it does:** expresses the `PATTERNS` set (`SAD-001#3.7`) as boolean DAG
  nodes consuming raw + indicator levels, so patterns compose in the same calculus.
- **Primary components:** SAD-002#5.1, SAD-001#5.6 (`PATTERNS`).
- **Acceptance posture:** each pattern node's flag matches `evalPatternAt` over the
  fixture series, including multi-bar and `n`-parameterised patterns.

### SAD-002#3.7 CAP-dag-compat: Backward-compatible public surface
- **What it does:** keeps the exported engine API and `PRESETS`/catalogues working
  on top of the new model, so no consumer changes (SAD-002#2.3).
- **Primary components:** SAD-002#5.4.
- **Acceptance posture:** the existing engine + component test suites pass unchanged
  with no edits to consuming components or the store.

### SAD-002#3.8 CAP-dag-fidelity: Differential fidelity harness
- **What it does:** a test harness that diffs old-engine vs new-engine output across
  indicators, presets, and PCF over the golden-master fixtures, gating CI.
- **Primary components:** SAD-002#5.5.
- **Acceptance posture:** the harness runs in CI and fails on any bar-for-bar
  divergence; it covers every indicator type, every `PRESETS` entry, and the PCF
  example (SAD-002#2.1).

### SAD-002#3.9 CAP-dag-schedulable: Schedulability contract
- **What it does:** exposes the DAG's topological order and per-(node, bar)
  addressability so the screening service (`SAD-001#4.2`) can later materialise
  lower levels once and prune — **without** implementing that move here. Also the
  hook the deferred temporal layer will sit on.
- **Primary components:** SAD-002#5.6.
- **Acceptance posture:** the engine exposes a stable topological ordering and a
  per-(node, bar) value accessor; a documented example shows lower-level nodes
  computable independently of any single rule. No server code is added (SAD-002#1.2).

## SAD-002#4 Containers

No new or changed containers. All work is inside the existing **engine module**
hosted by both the web client (`SAD-001#4.1`) and the screening service
(`SAD-001#4.2`), which continue to import the *same* engine (`SAD-001#8.3 / ADR-003`).
The DAG must therefore remain isomorphic (SAD-002#2.2).

## SAD-002#5 Components

Patterns to use and to avoid are called out because stories cite this section most.

### SAD-002#5.1 DAG node model — engine module (`src/lib/market.ts`, or a co-located pure module it re-exports)
The node type and node-kind constructors: raw-source (L0), aggregation
(`ema`/`sma`/`rsi`), composite (`macd`/`stochrsi`/`relVol`/price-vs-EMA), algebraic
(`+ − × ÷`), relational/boolean (`> < ≥ ≤ == !=`, `cross_*`), and pattern nodes.
Level is a derived getter.
- **Use:** keep nodes as **plain, serialisable data** (kind + input refs +
  params); derive level by walking inputs; keep everything pure and isomorphic
  (SAD-002#2.2). If split into a new file, co-locate under the engine and keep the
  module dependency-free.
- **Avoid:** storing closures/functions in nodes; mutating nodes after
  construction; hand-assigning levels; introducing a cyclic edge.

### SAD-002#5.2 Node evaluator + memo cache
Topological evaluator that, given an instrument's bars and a target node, computes
the node and its transitive inputs once each, memoised per (instrument, node id).
Replaces the `indSeries`/`defSig` cache mechanism (`SAD-001#6.2`) while preserving
its outputs.
- **Use:** evaluate bottom-up in topological order; memoise by node identity
  (SAD-002#6.1); prune to reachable nodes only (SAD-002#2.4); attach the cache to
  the instrument like today's `_indCache`.
- **Avoid:** recomputing shared inputs per referencing rule; evaluating
  unreferenced catalogue nodes; unbounded cache growth (SAD-002#2.7).

### SAD-002#5.3 Lowering layer — defs/rules/PCF → nodes
Pure functions mapping `IndicatorDef`, `Condition`/`GroupRule`/`ChainRule`/
`IndRule` operands (with bar offsets and `×mult/+add`), and `parsePCF` output onto
DAG nodes.
- **Use:** one lowering path shared by indicators, rules, and PCF so they cannot
  diverge; preserve bar offsets and arithmetic exactly; reuse `srcArr` source
  semantics (close/open/high/low/hl2/hlc3/volume).
- **Avoid:** a second PCF-specific evaluation path; re-implementing arithmetic
  differently from the algebraic nodes (SAD-002#3.4).

### SAD-002#5.4 Compatibility shims — preserved public API
Thin adapters that keep `indSeries`, the `eval*` functions, `backtestRules`,
`PRESETS`, and catalogues (`SAD-001#5.6`) exported with unchanged signatures,
implemented over the new model.
- **Use:** route old entry points through lowering (SAD-002#5.3) + evaluator
  (SAD-002#5.2); keep behaviour identical (SAD-002#2.3).
- **Avoid:** changing exported signatures; requiring consumers to adopt the node
  model in this plan.

### SAD-002#5.5 Differential fidelity harness (tests)
A test component that runs old vs new engine over the golden-master fixtures and
asserts bar-for-bar equality across indicators, presets, and PCF.
- **Use:** drive from the existing fixture universe (`SAD-001#8.7 / ADR-007`
  synthetic adapter); fail CI on any divergence; keep the *old* engine path
  available (e.g. pinned reference output) until parity is locked.
- **Avoid:** asserting on rounded/printed values instead of raw series; sampling a
  subset of bars when full-series parity is the contract.

### SAD-002#5.6 Schedulability interface
A small, stable surface exposing the topological ordering of a DAG and a
per-(node, bar) value accessor, for later server-side materialisation
(`SAD-001#4.2 / 2.5`) and the deferred temporal layer.
- **Use:** expose ordering + addressable node values as **read-only** engine
  output; document the contract.
- **Avoid:** baking any server/transport/materialisation decision into the engine
  here (SAD-002#1.2); leaking instrument I/O into the engine (SAD-002#2.2).

## SAD-002#6 Data

### SAD-002#6.1 Node & node identity
A **node** is `{ kind, inputs: NodeRef[], params }` where `kind` is one of the
SAD-002#6.2 taxonomy, `inputs` reference other nodes (raw sources have none), and
`params` carries op/parameters (e.g. period, operator, offset, mult/add). **Level**
is derived: 0 for raw sources, else `1 + max(level of inputs)`.
- **Node identity** is a **structural signature** over `(kind, params, input
  identities)` — the generalisation of today's `defSig` (`SAD-001#6.2`). Equal
  nodes share a key (enabling dedup, SAD-002#2.4); any change yields a new key
  (enabling correct invalidation, SAD-002#2.7).
- **Rule:** nodes are immutable, acyclic, and serialisable; identity is a pure
  function of structure, independent of instrument.

### SAD-002#6.2 Node-kind taxonomy (levels)
- **L0 raw-source:** `open/high/low/close/volume` and derived sources `hl2`,`hlc3`.
- **L1 aggregation:** `ema`, `sma`, `rsi` (Wilder), rolling/volume averages —
  inputs are raw only.
- **L2+ composite:** `macd` (EMAs → signal), `stochrsi` (rsi → stoch), `relVol`,
  price-vs-EMA — inputs include L1.
- **algebraic:** `+ − × ÷` over scalar inputs (carries any level by its inputs).
- **relational/boolean:** `> < ≥ ≤ == !=`, `cross_up`/`cross_down` — scalar inputs,
  boolean output.
- **pattern:** boolean multi-bar structure detectors (`SAD-001#3.7`) over raw +
  indicator inputs.

### SAD-002#6.3 Cache (derived, ephemeral)
Per-(instrument, node-identity) memoised series, attached to the instrument like
today's `_indCache`. Never authoritative; rebuildable from bars + nodes
(`SAD-001#6.2`). Invalidation is implicit: a changed node has a new identity, hence
a new key (SAD-002#2.7).

### SAD-002#6.4 Relationship to persisted artifacts (no migration here)
The persisted `IndicatorDef` and `Rule` shapes (`SAD-001#6.3 / 6.4`) are **not
changed** by this plan. Defs and rules continue to be authored, stored, and loaded
in their current JSON form; they are **lowered into nodes at evaluation time**
(SAD-002#5.3). **Rule:** no saved-artifact schema change and no migration of saved
artifacts in this scope — that would be a separate, explicit decision
(SAD-002#8.7 / ADR-007).

## SAD-002#7 Cross-cutting Concerns
- **Fidelity gate:** the differential harness (SAD-002#5.5) is cross-cutting — every
  story touching lowering or evaluation runs it.
- **Engine-purity boundary:** SAD-002#2.2 spans every component; the DAG and its
  evaluator take bars in and return values out, no I/O inside.
- **Cache discipline:** node identity is the single cache key; no component caches
  series by any other key (SAD-002#6.3).
- **Observability:** the node-evaluation counter used for SAD-002#2.4 is a
  test/instrumentation affordance, not a production dependency.
- **Forward-compatibility:** the schedulability interface (SAD-002#5.6) is the one
  designed seam for the deferred temporal layer and server materialisation; other
  components must not assume a flat series model.

## SAD-002#8 Decisions (ADRs)

### SAD-002#8.1 ADR-001: Model indicators as a computation DAG with derived levels
- **Context:** the flat per-`defSig` series model has no dependency structure to
  schedule, share, or prune (PLAN-002 problem; `SAD-001#2.5`).
- **Decision:** represent indicators/rules as an acyclic graph of immutable nodes
  with raw OHLCV at the root; level is derived as topological depth, never assigned.
- **Consequences:** shared sub-expressions dedup; computation becomes schedulable;
  level is a property of structure. Adds a node model and evaluator the engine did
  not have.
- **Status:** accepted

### SAD-002#8.2 ADR-002: Refactor in place; preserve the public surface; keep the old path until parity
- **Context:** numeric trust and a working product depend on the current engine
  (`SAD-001#2.1`); a rewrite risks both.
- **Decision:** lower existing indicators/rules into the new model behind unchanged
  exports (SAD-002#5.4); keep the old engine output available as the differential
  reference (SAD-002#5.5) until bar-for-bar parity is locked, then retire it.
- **Consequences:** no consumer churn (SAD-002#2.3); fidelity is provable; a
  transitional period maintains two code paths.
- **Status:** accepted

### SAD-002#8.3 ADR-003: Node identity is a structural signature; memoise per (instrument, node)
- **Context:** `defSig` already keys the current cache per def; the DAG needs a key
  that also captures inputs and composite structure.
- **Decision:** define node identity as a pure structural signature over `(kind,
  params, input identities)`, generalising `defSig`; the evaluator memoises per
  (instrument, node identity).
- **Consequences:** equal sub-expressions are computed once; any structural change
  invalidates correctly; identity is instrument-independent and serialisable.
- **Status:** accepted

### SAD-002#8.4 ADR-004: Algebraic & relational operators are first-class node kinds
- **Context:** arithmetic lives today as per-operand `×mult/+add` and source
  derivations (`hl2`/`hlc3`); comparisons live inside `cond`/`chain`/`ind`
  evaluators. PLAN-002 open question: first-class nodes vs. generalised operands.
- **Decision:** make `+ − × ÷` and `> < ≥ ≤ == !=`/`cross_*` **first-class node
  kinds**, and **lower** the existing per-operand arithmetic and comparison
  operators into them — one arithmetic/comparison implementation, not two.
- **Consequences:** uniform composition and a single source of truth for operators;
  the lowering layer must reproduce the exact existing arithmetic/cross semantics
  (SAD-002#2.1).
- **Status:** accepted

### SAD-002#8.5 ADR-005: Patterns become boolean DAG nodes, semantics preserved
- **Context:** `evalPatternAt` is a separate per-bar evaluator (`SAD-001#3.7`).
- **Decision:** expose patterns as boolean DAG nodes consuming raw + indicator
  levels so they compose in the calculus, while preserving the exact `evalPatternAt`
  truth values.
- **Consequences:** patterns participate in the DAG (and later the temporal layer);
  pattern flags must match the POC bar-for-bar (SAD-002#3.6).
- **Status:** accepted

### SAD-002#8.6 ADR-006: Temporal sequencing is deferred; reserve the seam
- **Context:** temporal operators (`THEN`/`WITHIN`/`WHILE…never`/onset) are the
  largest, riskiest piece and are out of scope (SAD-002#1.2).
- **Decision:** do **not** build temporal sequencing now; instead expose the
  schedulability interface (SAD-002#5.6) — topological order + addressable
  per-(node, bar) values — as the documented seam the temporal layer will sit on,
  so it lands without a second refactor.
- **Consequences:** scope and risk contained; a later temporal plan extends rather
  than rewrites; components must not assume a flat series model.
- **Status:** accepted

### SAD-002#8.7 ADR-007: No persisted-artifact schema change or migration in this plan
- **Context:** saved `IndicatorDef`/`Rule` artifacts (`SAD-001#6.3 / 6.4`) are the
  only mutable user data; changing their shape would force a migration.
- **Decision:** keep the persisted def/rule JSON unchanged; lower them into nodes
  at evaluation time (SAD-002#5.3). Any future "store the DAG" decision is separate
  and explicit.
- **Consequences:** zero migration risk; saved artifacts keep working; the node
  model stays an internal/runtime representation in this scope.
- **Status:** accepted

### SAD-002#8.8 ADR-008: Schedulability without server implementation
- **Context:** the primary driver is scalability (`SAD-001#2.5`), but moving compute
  to the screening service is large and is out of scope here (SAD-002#1.2).
- **Decision:** deliver only the *enabling contract* — a topological ordering and
  per-(node, bar) addressability (SAD-002#5.6) — and prove lower levels are
  computable independently of any single rule; do not add server/transport/
  materialisation code.
- **Consequences:** the scale follow-through has a clean seam to build on; this plan
  stays a pure-engine refactor with no container change (SAD-002#4).
- **Status:** accepted
